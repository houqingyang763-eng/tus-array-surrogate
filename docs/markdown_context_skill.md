# Markdown 上下文管理 Skill v1

## 触发词

当用户说“markdown”时，默认含义不是普通排版，而是：

> 总结刚刚讨论过的某个内容，整理成适合 AI 长期上下文管理 / project prompt / promote 使用的 Markdown 结构。

## 目标

输出内容要服务于：

1. 更好地管理项目上下文；
2. 让另一个 AI 或未来对话快速接上当前共识；
3. 固化刚刚讨论出的判断、规则、偏好、模板、分类或路线；
4. 减少后续对话的信息损失。

## 输出原则

1. 使用 Markdown。
2. 优先写成可复制到 project instructions / promote / memory 的形式。
3. 不写闲聊。
4. 不写过多解释。
5. 不重复无关背景。
6. 保留关键判断，而不是流水账。
7. 面向 AI 使用，因此要明确规则、触发条件、优先级、禁止事项。
8. 如果刚刚讨论的是模板，就输出模板。
9. 如果刚刚讨论的是项目判断，就输出项目判断。
10. 如果刚刚讨论的是论文分类，就输出分类规则。

## 默认结构

根据内容选择合适结构，常用结构包括：

### 1. 背景

说明这个 Markdown 适用于什么项目、什么阶段、什么任务。

### 2. 当前共识

列出刚刚讨论后已经确定的判断。

### 3. 优先级

说明什么最重要，什么次要，什么暂时不做。

### 4. 执行规则

说明以后遇到类似任务时应该怎么做。

### 5. 输出模板

如果用户是在训练某种回答格式，则写成固定模板。

### 6. 禁止事项

说明以后不要怎么做。

### 7. 关键词 / 检查清单

列出后续 AI 应该持续关注的关键词或判断点。

## 风格要求

1. 清楚；
2. 可执行；
3. 结构化；
4. 面向后续 AI；
5. 不空泛；
6. 不堆砌；
7. 直接可复制。

## 当前项目中的特殊要求

在“经颅超声 3D 阵列设计神经网络加速”项目中，当用户说“markdown”时，尤其要注意：

1. 先保留大局判断；
2. 不要拆成太多任务；
3. 不要把 Trello 塞满；
4. 所有总结都要服务组会 PPT 和论文整理；
5. 论文相关内容要围绕：
   - 阵列设计；
   - 阵列位置可变；
   - 阵列形状可变；
   - 3D；
   - 单阵元响应预测 + 叠加；
   - peak pressure + brain pmax field；
   - array geometry variation。
6. 输出要适合用户复制进项目指令。
