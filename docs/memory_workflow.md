# 科研记忆与自主推进工作流 v4

## 目标

本 repo 同时承担两项职责：

1. 保存稳定、可追踪、不过度冗余的科研记忆；
2. 让 Codex 在用户批准的边界内自主推进少量 Research Mission。

它不替用户生成大量 todo，也不允许 Agent 把推测直接升级为项目结论。

---

## 四层结构

### 1. 稳定知识层

- `docs/project_concept_v7.md`：当前源构想；v6 及更早版本为历史来源；
- `docs/memory.md`：当前状态、近期关注、每日任务及其总结、反向时间线；
- `docs/decisions.md`：稳定共识；
- `docs/ideas.md`：未验证但有价值的想法；
- `docs/questions.md`：真正开放的问题。

### 2. 任务合同层

- `docs/research_tasks.md`：只保存 1-3 个用户批准的自主研究 mission；
- 每个 mission 必须包含权限、禁止事项、证据标准、交付物、资源预算、停止条件和人工验收；
- 不把所有 idea / question 自动转成任务。

### 3. 执行与证据层

- `docs/agent_runs/<mission-id>/`：保存中间报告、证据表和待审方案；
- 主 Agent 负责范围、综合和最终汇报；
- 子 Agent 负责独立取证、比较、测试或质疑；
- 子 Agent 不直接修改核心记忆。

### 4. 人工验收层

用户负责：

1. 学习任务涉及的关键知识；
2. 批注 Agent 判断；
3. 决定哪些内容进入 ideas / questions / decisions / project concept；
4. 批准后续 mission 或扩大权限。

---

## Token 经济规则

1. `memory.md`、任务队列和运行报告默认最新内容在最上面；
2. 文件开头先给当前有效状态，再给历史；
3. 历史细节尽量通过链接指向专门日志，不在多个核心文件重复粘贴；
4. 稳定参考文档按概念结构组织，不为倒序而牺牲可读性；
5. 旧内容被替代时保留简短状态和依据，完整旧版本依靠版本文件或 Git 历史追踪。
6. 给用户的长篇研究汇报、解释和论证直接放在对话中；Markdown 只保留供 Codex 快速读取的简洁决定、状态、边界和证据入口，除非用户明确要求独立长文档。

### 网络设计决策清单

网络设计汇报先穷举具体设置和软件隐含默认值，每项标注“已确认 / 暂定 / 候选 / 未确定”，便于用户逐条圈画批注。基础概念教学移到独立学习对话；当前决策对话只负责候选、证据、取舍和确认。

依据：用户 2026-07-24 对 A2b 参数清单汇报方式的明确认可。

## 记忆分类

### `docs/memory.md`

只保存：

1. 当前状态摘要；
2. 当前 3-5 个关注方向；
3. 当天少量、任务导向的学习 / 研究计划及日终总结；
4. 最新到最旧的关键时间线；
5. 已舍弃 / 已降级路线；
6. 活跃 mission 的简短索引。

不写聊天流水账、实验逐行日志或碎片化 checklist。每日任务只保留真正推动项目理解或判断的 1-5 项，不把阅读页码、临时命令和细小动作拆成独立任务。

### `docs/ideas.md`

记录来源、想法、依据、可能价值和待验证点。未经验证不得写成结论。

### `docs/questions.md`

记录需要问人、查论文或做实验才能回答的问题。已舍弃路线不再作为活跃问题。

### `docs/decisions.md`

只在以下条件下写入：

1. 用户明确确认；
2. 组内反馈明确要求；
3. 论文、代码或实验给出足够证据；
4. idea / question 经用户确认升级。

### `docs/research_tasks.md`

只记录用户批准的 mission，不记录普通 todo。旧任务迁移摘要见 `docs/research_tasks_archive.md`。

## 日常记忆流程

```text
用户输入 / 论文 / 代码 / 实验
-> Codex 判断来源类型和证据等级
-> 提出 memory / idea / question / decision 的更新建议
-> 用户确认
-> 主 Agent 写入核心文件
-> 汇报修改、未写入内容和风险
```

如果用户已经明确要求执行一份此前批准的变更清单，可以直接写入，不重复确认。

### 任务导向的每日跟进

每日学习 / 研究日志采用“问题触发任务，任务产生总结”的结构。它记录的是用户当天要推进的少量学习任务，不等同于 `docs/research_tasks.md` 中授权 Codex 自主执行的 Mission。

每天开始时，在 `docs/memory.md` 最前部新增“今日任务”。每项只需几行，允许问题和行动方向保持一定模糊度：

```text
任务标题
问题 / 想法：为什么今天想查这件事
今日行动：大致准备怎样学习、检查或尝试
状态：todo
```

不要求早上预先写时间预算、阅读页码、详细产出、完成标准或复现门槛。每日计划的作用是保留“问题怎样产生，随后去做了什么”的因果线索，不是提前写一份精密项目合同。

当天结束时，再根据实际发生的探索在每项任务下面详细补充：

```text
当日总结：实际做了哪些阅读、讨论、代码检查或实验
探索结果：学懂了什么，发现了什么问题
证据 / 产出：论文、代码、实验记录或讨论入口
判断边界：哪些已有证据，哪些仍只是想法
遗留问题 / 下一步：是否继续，为什么
```

执行规则：

1. 先写任务，再开始学习或检查，避免日志退化为事后流水账；
2. 早上的任务保持简短；探索尚未发生时，不预写大量细节；
3. 晚上的总结可以详细，因为它记录真实发生的过程和结果；
4. 未完成任务标记 `partial / deferred / blocked` 并写明原因，不默认复制到下一天；
5. 第二天建立新计划时，把前一天已结束的任务压缩进反向时间线，但保留逐项总结和证据入口；
6. 日志中的稳定结论、开放问题和新想法，仍按证据等级分别迁移到 `decisions.md`、`questions.md`、`ideas.md`，不能因为“当天完成”就自动升级为项目共识；
7. 只有 `docs/research_tasks.md` 中的自主 Mission 才需要预先写清交付物、完成标准、预算和停止条件。

## 实验来源与复现规范

### 来源硬门槛

除纯工程探针外，任何仿真、深度学习训练或 idea 可行性验证都必须建立在可追踪来源上。可接受来源为：

1. 论文作者或机构官方代码；
2. 论文明确链接的补充代码、数据或归档版本；
3. 经论文结构、配置、指标和结果核对的第三方复现。

不得用临时自设计模型替某篇论文方法受审，也不得在缺失核心代码时自行补写一个相似实现后继续使用原方法名称。

### 无需来源的简单例外

只有以下不会对科研方法可行性作结论的纯工程探针可以自写：

- 显存占用；
- 查询 / 推理吞吐；
- 张量形状与数据类型；
- 文件读写与数据格式；
- 确定性公式、单位换算或代数恒等式单元测试。

这些结果只能说明本机资源、接口或实现流水线状态，不能证明网络架构、物理路线或论文方法有效 / 无效。

### 实验来源字段

每项正式实验的 README、配置或运行元数据必须包含：

```text
method_source:
implementation_source:
source_commit_or_release:
reproduction_level: unchanged | environment_port | data_adapter | custom
changes_from_source:
claim_boundary:
```

等级含义：

- `unchanged`：作者示例原样运行，只改变路径和设备选择；
- `environment_port`：只修复依赖、版本、路径或平台兼容，不改变方法；
- `data_adapter`：核心网络、损失、优化器和初始化不变，只适配输入数据格式；
- `custom`：修改或新建网络、损失、优化器、初始化、输出头或任务定义。

`custom` 只能作为工程探索，必须改用自定义名称；除非用户另行批准且有独立证据，否则不能用于某篇论文方法或科研路线的生死判断。

### 复现顺序

```text
核对论文—代码对应关系
-> 固定仓库版本 / commit 和环境
-> 原样运行作者最小示例
-> 核对论文指标或图表
-> 原样复现通过后再制作数据适配器
-> 逐项记录修改及其证据边界
```

修改网络、损失、优化器、初始化或输出头必须再次获得用户明确批准，并改名为“基于某方法的自定义改造”。如果原实现不支持项目所需物理量，例如复数输出，不得擅自增加通道后继续声称原方法已被复现或验证。

## 自主 Mission 流程

```text
候选问题
-> 主 Agent 起草 mission contract
-> 用户批准
-> 在独立任务 / Worktree 中执行
-> 子 Agent 返回证据与分歧
-> 主 Agent 写入 docs/agent_runs/<id>/
-> 用户学习与验收
-> 经批准后更新核心记忆
```

默认无需再次确认的动作，仅限 mission 合同明确授权的范围。

必须再次确认：

1. 修改 `project_concept_v*.md` 或 `decisions.md`；
2. 安装依赖或改变系统环境；
3. 运行超出预算的 GPU / 长时间任务；
4. 删除原始数据或历史文档；
5. 上传、发布或共享外部内容；
6. 扩大 mission 研究范围。

## Agent 运行交接格式

每次自主任务结束必须回答：

1. 我帮你做了什么；
2. 哪些是有证据的事实；
3. 哪些只是 Agent 推测；
4. 哪些尝试失败或被停止；
5. 建议怎样更新项目记忆；
6. 哪些决定必须由用户做；
7. 用户必须学习哪些概念、图表、公式或代码路径；
8. 用什么问题检查用户是否真正理解。

---

## 论文导读边界

论文精读的主体是用户。Codex 可以完整预读，但默认只交付一份简洁导读：价值判断、结构地图、最多 5 个关键审计问题、理论分块和阅读路线。

默认使用单 Agent。多 Agent 论文精读和 taste 校准试点已停止；只有用户明确要求对一个窄问题做独立复核时，才使用额外 Agent。

去重要求：

1. 不同时生成主报告、逐节证据审计、技术深挖和批注模板；
2. 不在多个章节重复“能偷 / 不能偷”和项目逐项对照；
3. 不重复用户已掌握的稳定项目结论；
4. 细碎缺口必须合并成不超过 5 个真正影响论文判断的问题；
5. 详细证据只有在用户追问时再展开。

## 依据标签

关键结论尽量标注：

```text
用户确认
项目文档
论文原文
代码 / 数据实证
实验结果
计算推导
Agent 推测
```

来源不明或证据不足的内容只能进入 idea / question / agent run 草稿。
